The Fast Fourier Transform is one of the most important innovations in digital signal processing and one of my favorite algorithms. The FFT is a fast way to extract the frequency content of signals, letting you rapidly analyze, filter, and manipulate frequencies across different bands of the spectrum. The Fourier transform computes the energy in each frequency band through a simple dot product. 1 Let x denote your input, a length n array of samples, and f a frequency. Then the amount of frequency content in x at f can be computed by the formula: For digital signals, a bit of math shows you only need to compute n of these dot products, one at each multiple of the frequency 2&#120587;/n, to understand all of the frequency content. Naively, this requires n multiplications and additions for each frequency. Hence, computing the entire Fourier transform appears to require n 2 arithmetic operations. The fast Fourier transform is a clever recursive procedure devised by James Cooley and John Tukey in 1965. 2 The main idea is that a length-n Fourier transform can be computed by shuffling the input vector, computing two Fourier transforms of length n/2 on the shuffled components, and then recombining the outputs using atomic arithmetic operations. The shuffles and recombinations take a linear number of arithmetic operations. Repeating this procedure iteratively, namely, log 2 (n) times, computes the full discrete Fourier transform. With the bookkeeping, the FFT computes a length-n Fourier transform in fewer than 5 n log2 n arithmetic operations. To make this acceleration concrete, when n is 1,000, n^2 is 1,000,000 and 5 * n log n is around 50,000, a 20-fold speedup. When n is 1,000,000, the speedup is 10,000-fold. These speedups can be the difference between a transform being computable or not given the constraints of a signal processing application. Since the invention of the FFT, people have looked for even faster Fourier transforms. One question is just how fast you can go. It seems like you probably need at least n operations to compute the FFT, as it takes n steps just to write it down. The FFT is 5*log 2 (n) times slower than that reasonable speed limit, and that 5*log 2 (n) factor can be big. It&#8217;s 200 when n is a trillion. Can you do something clever to reduce that prefactor of 200? Instead, I found the rot that develops inside applied mathematical theory when formalism becomes so detached from reality that a &#8220;breakthrough&#8221; is nothing more than an artifact of mathematicians not being able to properly specify the rules of their games in natural language. First, &#8220;big-O&#8221; notation has been so abused that it has become meaningless. Let&#8217;s review the definition, which impressed me as an undergrad. An algorithm has running time T(n) = O(F(n)) if there exists an integer N and a constant C such that That is, the number of steps the algorithm actually takes is upper bounded by a constant times some convenient function F(n) as long as n is large. F(n) is usually something familiar and interpretable, like a polynomial or exponential function. This notation says that we only care about what happens when the size of the computation is large. We care about the asymptotic growth rate of the computation time. All constants are equivalent. Big-O notation is useful for shortcuts in algorithmic accounting, but it also allows for remarkable logical laziness. If we want a practically faster FFT, we want an algorithm that requires fewer than 50n operations for reasonably sized n. But O(n) does not mean 50 n. It could mean 10 80 n. This would be considered a &#8220;linear time&#8221; algorithm. An algorithm that requires n + 10 80 is also considered a linear time algorithm in the big-O regime. An algorithm that only has linear-time guarantees when n is greater than 10 80 is also considered linear time. 10 80 is approximately equal to the number of atoms in the known universe. That is why Richard Lipton and Ken Regan call algorithms with unfathomably large hidden constants galactic algorithms . The OpenAI FFT algorithm is definitely galactic. Lipton and Regan argue galactic algorithms are useful because they spur research. Once you show a running time is asymptotically possible, you can spend your time finding an algorithm that practically achieves this provable running time. Maybe you can send your AI agent swarms after it. You do you. Maybe you can get a practical algorithm out, but I don&#8217;t know of any legitimate examples where this happened. I&#8217;m particularly doubtful here, because the model of &#8220;computation&#8221; OpenAI uses bears no resemblance to an actual computer. &#8220;The model uses exact complex arithmetic.&#8221; That means it assumes you can store and multiply complex numbers at arbitrary precision. Indeed, the algorithm requires you to multiply complex numbers whose magnitudes grow superpolynomially with n. If you stored these numbers as bits, the memory requirement would effectively be exponential in the input length. It assumes you can multiply such arbitrarily large complex numbers together in a single operation. We do not have computers that can do this. So even if this theorem in main.pdf is &#8220;true&#8221; (no one knows, and I don&#8217;t care), it&#8217;s not actually solving the problem we set out to solve when looking for a faster FFT. For people familiar with theoretical analyses of the FFT, that you need an absurd model of computation to break the FFT speed limit isn&#8217;t surprising. In 1973, Jacques Morgenstern proved that you couldn&#8217;t get a Fourier transform faster than &#189; n log n if you required that complex coefficients used in the computation had bounded magnitude. That should have been the end of the story! But it wasn&#8217;t. People said Morgenstern&#8217;s restricted coefficient model was too restrictive. Forty years later, Nir Ailon showed that you couldn&#8217;t compute an FFT faster than n log n without severe numerical instabilities . This was also too restrictive for some people, I guess. This new OpenAI result is thus less a mathematical breakthrough and more an oddity of computer scientists being bad at formalizing their design specifications.
