At a high level, coding agents have a basic architecture: an LLM calls tools in a loop, while carrying forward the required context. Since that&#8217;s easiest to implement locally , many coding agents started out as terminal tools and then desktop apps (Claude Code famously began as a CLI tool). But as the open laptop meme illustrates, modern agent harnesses have frustrating limitations if they&#8217;re not able to be managed in the cloud . Since 2025, both OpenAI and Anthropic have been trying to shift their harnesses more into the cloud &#8212; but with varying levels of success. The challenges include keeping sessions reliable, isolating tool execution and preserving context. This sounds a lot like container orchestration in the early 2010s , from which emerged the open source Kubernetes in 2014. Kubernetes, developed by Google, became the dominant open source system for deploying and managing cloud applications at scale &#8212; it kickstarted the &#8220;cloud native&#8221; era of computing . Kubernetes uses control loops to keep applications running, recover from failures, and scale when needed. What if coding agents could be managed in the same way? That&#8217;s the bet that two Kubernetes creators, Craig McLuckie and Joe Beda , are making with Stacklok . Stacklok architecture; diagram via Stacklok Stacklok raised a $17.5 million Series A back in 2023 from Accel, Madrona and Bain Capital. Initially focused on software supply chain security , the company recently pivoted to Kubernetes-based agentic solutions . Mecatl: a harness built for the cloud The most interesting product of Stacklok is Mecatl, a &#8220;cloud-native harness&#8221; begun in June as an open source project on GitHub . At first, I thought the name was pronounced &#8220;me-cattle&#8221; &#8212; a play-on-words referencing the &#8216;cattle vs. pets&#8217; concept of Kubernetes, where you treat your servers, pods and clusters like cattle rather than pets. But no, the name is actually pronounced &#8220;MEH-kah-tl&#8221; and is an Aztec word meaning a cord or rope ! In any case, what does cloud-native mean in the context of a harness? It&#8217;s primarily about &#8220;moving the locus of value from the desktop to the cloud,&#8221; said McLuckie. He&#8217;s talking about &#8220;value&#8221; from an enterprise perspective &#8212; that the code and context are often derived from local environments. &#8220;That&#8217;s where the IP sits,&#8221; Beda chimed in. &#8220;And if you want to be able to actually bring that under management, it&#8217;s that much more difficult when it&#8217;s sitting on a desktop.&#8221; McLuckie added that a cloud native approach also allows Stacklok to ask some deeper questions about agentic coding. &#8220;Why is the agent loop so intricately coupled to the tool calling subsystems? Why is agent identity being reasoned about through the lens of human identity systems?&#8221; Diagram via Mecatl GitHub When it comes to open source agent harnesses, there are already well-regarded solutions &#8212; such as Pi , a &#8220;minimal agent harness&#8221; that projects like Flue have built on top of . We asked the Stacklok pair what makes their harness different? Beda didn&#8217;t mention Pi specifically, but he did say that in desktop-first harnesses, the loop, local execution and session state often begin inside the same process. &#8220;There are a ton of solutions in this space, but they&#8217;re all focused to essentially run on the desktop,&#8221; he said. &#8220;So even if they have pluggability, the architecture is still one process, or one set of tightly coupled processes, that are built to run on the desktop. &#8221; A Kubernetes deployment of Mecatl; via GitHub But can&#8217;t enterprises use VMs, containers, or one of many different sandbox products to move their harness to the cloud? Beda says this &#8220;lift and shift&#8221; approach tends to create issues around the lifecycle of an agent or being able to quiesce it (safely pause it while it waits for human input). &#8220;Our thinking is, well, what if we rethought the harness from the ground up to actually run in the cloud?&#8221; Separating the agent loop from execution One of the intriguing approaches of Mecatl is that it keeps the agent loop independent of the client, model provider, state store and execution environment . &#8220;This is an application that we know how to run in the cloud well,&#8221; said Beda, regarding the loop application. &#8220;What if we take that and we separate that out from the more sensitive operations , like tool calling and bash, and then also separate out things like session management and memory, so that these things are no longer stored as JSONL files sitting on disk, but can natively be put into manageable systems&#8221; Mecatl architecture; diagram via the project GitHub A lot of you reading this will probably have very opinionated harnesses, customized for your own requirements. But Mecatl is designed to extend beyond a single-user, local harness into infrastructure that enterprises can operate centrally. Beda likened this to how enterprises manage email. &#8220;We think, in the future, interactions that you have with an agent while you&#8217;re working for an enterprise belong to that enterprise; and they&#8217;re going to want to manage that and govern that like they do email.&#8221; Decoupling AI agents from frontier labs One of the main motivations of Stacklok is to help large enterprises lessen their dependency on frontier labs and hyperscalers , such as Codex, Claude Code and GitHub Copilot. This, suggested McLuckie, is similar to how Kubernetes helps companies reduce dependency on the big cloud providers. For McLuckie, the term &#8220;cloud native&#8221; came to represent a way to &#8220;run in a cloud that is decoupled from the specifics of the cloud provider. So a lot of what we&#8217;re trying to do [at Stacklok] is more or less what we did in the Kubernetes time.&#8221; After its pivot into agent infrastructure, Stacklok built ToolHive &#8212; an open-source platform for running and governing MCP servers. It initially began as a way to manage MCP servers running in Docker containers on the desktop. Then, said Beda, they expanded it into a &#8220; Kubernetes-based gateway and other associated services &#8212; a registry and an operator helper for running and managing MCP servers and getting some of the input-output auth stuff right with those things.&#8221; Diagram via project GitHub The idea, as McLuckie put it, was to enable enterprises that already ran on Kubernetes to &#8220;start to bring agentic workloads into those environments .&#8221; Beda claims that many other agent tools were designed for individuals or small startup teams, which doesn&#8217;t fly for enterprise-scale companies. &#8220;We talk to larger organizations and they&#8217;re struggling with like, how do I take this thing that was built for a team of six people and deploy it for an engineering task force in the thousands or tens of thousands.&#8221; Stacklok&#8217;s LLM gateway MCP was the first step. Next was building an LLM gateway , or &#8220;AI Gateway&#8221; as it&#8217;s called on the Stacklok&#8217;s website, to help companies control access and costs. &#8220;Most of our customers are banks, semiconductor companies, telcos&#8230;you know, people operating in relatively regulated industries,&#8221; McLuckie said. Stacklok&#8217;s &#8220;AI Gateway&#8221; a.k.a. LLM gateway The AI Gateway is the one main product Stacklok hasn&#8217;t open sourced yet, but Beda says it&#8217;s &#8220;on our roadmap and we&#8217;re going to get there soon.&#8221; Unlike Glean&#8217;s solution , Stacklok&#8217;s AI Gateway does not currently choose a model based on the task.
