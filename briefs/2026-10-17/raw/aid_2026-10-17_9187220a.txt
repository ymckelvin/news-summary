DevPods, Code Inbox, Slate and Wisdom: four of the 20+ internal tools Uber engineers use,day-to-day Today&#8217;s episode is a deepdive into the day-to-day tools of devs at Uber, our tour guide being on of Uber&#8217;s longest-tenured engineers: Uday Kiran Medisetty . Uday is one of the few Distinguished Engineers at the company, and leads much of the work on agentic AI, today. With Uday, we talk through how Uber&#8217;s developer infrastructure prepared it for AI agents. We look at the systems Uber built before generative AI and the new tools that connect agents to its code, internal services, and engineering knowledge. Uday explains how engineers use background agents, why tools like Slate make development (and bugfixing!) more efficient, and how code review is changing. We also cover Uber&#8217;s approach to token costs and how it measures productivity as the engineer&#8217;s role changes. Takeaways from the conversation with Uday Here are 11 interesting learnings from today&#8217;s episode: 1. Uber&#8217;s service count changed erratically: in 2015, when Uday joined, there were two services in total. By 2019, there were thousands. In 2026, there will be about the same number of services than in 2019, even though the business is about 10x larger than back then! 2. Uber built most services in-house because off-the-shelf software could not handle its scale &#8211; or simply did not exist! Examples of services Uber built because it had to: uOwn : shows who owns a service or asset. Back in 2015, no such vendor existed. M3DB : Uber was emitting about 500 million metrics per second, with no vendor being able to handle this load, so they built it themselves. Observability company Chronosphere was built on top of the open sourced M3DB, and we previously covered how Uber built its observability platform . Cadence : a durable workflow engine for multi-day flows like driver onboarding. No such system existed at the time when Uber needed it. Temporal was built on top of the open sourced Cadence framework. Morpheus : a system combining feature flags and experimentation, including switchback tests, with support for two- and three-sided marketplaces that Uber operates. Again, no such solution existed when Uber needed it. 3. At Uber, cities are a first-class concept that go all the way down to physical infrastructure. Another reason Uber had to build a lot of its custom tooling is how the concept of cities is a &#8220;basic primitive&#8221; that needs to be handled across systems like observability, feature flagging, deployments, and even service sharding. For example, in the early days, some services had their database sharded by cities. Even today, each city is pinned to a cloud region, and can fall over to another region at any time. We previously covered how Uber moved from bare metal to the cloud . 4. A single AI model gateway has paid lots of dividends. In 2023, Uber&#8217;s platform team made the decision that everything built with AI needs to be model- and harness-agnostic. They built Model Gateway to support switching between Anthropic, OpenAI, other vendor models, and now also supports open models they run. Having the Model Gateway in place made it easy to extend with these parts: AI Guard : a middleware run by the security team. It checks all requests and responses, and measures latencies (and flags overly slow models or queries) Spend tracking: spend is tracked per user Visibility : audit logs and session traces 5. AIFX allows engineers to switch harnesses without losing settings. Uber currently supports Claude Code, Codex, and OpenCode as harnesses. AIFX (short for AI Foundations) is a wrapper on top of all of these, so when an engineer changes harnesses, all their settings, skills and plugins move with them. 6. Uber has a hybrid approach to AI spend: engineers get allocated a spend tier. When they hit the limit, their manager can sign off to spend more in that month. Basically, for the right type of work, there is no spend limit, but Uber doesn&#8217;t want engineers to carelessly burn tokens. A plugin called CostCheck works across sessions and gives tips on how to improve an engineer&#8217;s cost profile. Uber has reduced token costs by about 50% the last few months, as we previously covered. 7. All PRs are still reviewed by engineers, but Uber built tools to help devs decide how much time they need to spend on each code change. Uday admits that code review has become a big bottleneck inside the company, and Uber built Code Review to make it easier and more efficient for devs to do these reviews. By the time a dev reviews a change, AI code review has run, screenshots and videos of the feature have been added (when applicable), and risk scores are assigned to the change. 8. Uber had to declare an internal &#8220;code red&#8221; for its CI system earlier this year. This was because CI jobs more than doubled in a 12-month timeframe, pushing load on CI systems overly high. To keep build speeds at bay, the team moved simple CI jobs (eg linting, build and template rules) to the &#8220;inner loop:&#8221; so agents run these commands with the afx validate command before opening a PR. 9. Uber tags PRs by the type of work each of those PRs do. In the past, Uber measured &#8220;PR velocity:&#8221; how long it took for a PR (or, as Uber calls it: a &#8220;diff&#8221;) to get to production. With agents, doing so makes less sense, because it&#8217;s easy to create dozens or even hundreds of PRs, and many of those PRs might have no business impact on the product. &#8203;So Uber now tags all PRs by type: feature, bugfix, maintenance, testing, or docs. &#8203;They are seeing the percentage of &#8220;feature PRs&#8221; going up, and the percentage of &#8220;maintenance PRs&#8221; going down.&#8203; I find this categorization to be a clever approach! 10. The job of a software engineer inside a place like Uber is to build context. As Uday reflects on how the job has changed: &#8220;The job of engineering is, in some sense: &#8216;how do you build the right context for the agents to produce reliable output?&#8217; You need to get really good at context engineering. Also, [being good at] multitasking has become a thing. Before, it would take so much time to create a PR, so you would be laser-focused on it. But now you&#8217;re constantly switching between so many things. You need to be able to verify your work and pick any code smells from the agent [to avoid] shipping regressions into production.
